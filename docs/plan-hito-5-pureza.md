# Plan del Hito 5 de la pureza: la venta, la frontera de la carta y el cierre de la rama

Estado: plan de ejecución (2026-10-08), armado con tres planificadores (Opus) que leyeron el código real en `d505ecbe`. Lista de control: `docs/pureza-integracion.md` (filas 5.1 a 5.4, O.13, O.32). Se ejecuta **en serie** (la base de tests es compartida y las listas de guardianes se pisan), con agentes de implementación Sonnet 5.5 y auditoría final con Opus.

## 0. Reglas que valen para todos los pasos

1. Un commit por paso; `git add` por nombre, verificando que no falle; asunto corto + cuerpo; trailers de atribución del sistema. Sin push, sin `--no-verify`, sin amend.
2. Antes de cada commit: `npx tsc --noEmit` (vitest no chequea tipos), `npx eslint <archivos>`, `npm run arquitectura` (leer «no dependency violations found»), `npm run analizar:muerto` (knip 0) y los tests de la zona.
3. **Un solo proceso de vitest a la vez** (`fileParallelism: false`; la base de tests se trunca). Los tests de concurrencia, 3 corridas.
4. **Toda regla o test nuevo se prueba por mutación**: rojo con el cambio que debería ponerlo en rojo → revertir **editando** (nunca `git checkout --` sobre cambios sin commitear del paso) → verde. Si una mutación no da rojo, se cierra con un test nuevo o se informa.
5. Goldens, huellas y caracterizaciones existentes **no se editan** (`venta-matriz*`, `lecturas-tramo-a`, `reportes-c0`, `huella-del-pos`, `dinero-tramo-c`, `test/permisos/caracterizacion/*`, `test/auth/caracterizacion/*`). `src/server/acceso/gate.ts` no se toca. Nada de schema, migraciones, `prisma/`, `package.json`, `vercel.json`. Lo nuevo de `core` nace P0 (sin `@prisma/client`).
6. Escribir TS y editar tests solo con las herramientas de edición/escritura de archivos (nada de heredocs ni one-liners para editar).
7. El codemod de imports (`npm run reapuntar:imports -- --desde … --hacia … [--nombres …]`) primero en simulacro (sin `--escribir`), con la lista revisada. **No reescribe** `vi.mock`, `typeof import("…")` ni `export … from`: eso va a mano.
8. Mudanza pura = mismo nombre, misma firma, mismo cuerpo. Se prueba con las redes existentes idénticas (RED-VENTA, abajo) y con `diff` de cuerpos.

**RED-VENTA** (un solo proceso, en serie): `npx vitest run test/movimientos test/auditoria/concurrencia-arrastre-redondeo.test.ts test/auditoria/precision- test/auditoria/concurrencia-idempotencia.test.ts test/auditoria/idempotencia-i3-mecanismo.test.ts test/pos/caracterizacion test/pos/cerrar-cuenta test/casos-de-uso/registrar-venta.test.ts test/core` más `npx vitest run test/arquitectura`.

## 1. Orden de ejecución

5.1 (bloques A y B) → 5.2 (bloques 1 y 2) → 5.3 → 5.4 (bloques A, B y C) → gate final, auditoría, cierre. Motivo: 5.3 necesita que `precio-venta` haya salido de `core/movimientos` (5.2 paso 1) y 5.4 necesita las capacidades fuera de `core/permisos`. ## 2. Hallazgos de base (verificados)

- `armarLinea` y `cargarDeudaDeRedondeo` son funciones privadas de `src/server/actions/movimientos/casos-de-uso/registrar-venta-en-tx.ts` (aprox. líneas 72-148 y 160-168). `armar-linea-de-movimiento.ts` es otro motor (movimientos genéricos) y NO se toca.
- Las lecturas y los rechazos de `armarLinea` están intercalados con salida temprana, y los goldens registran el multiconjunto de lecturas también en los rechazos: **no se puede «cargar todo y después decidir»**. El orquestador queda en el caso de uso con el mismo orden de lecturas; se extraen las lecturas a `server/lecturas` y las reglas a `core`.
- `core/movimientos` no queda 100 % P0 en esta rama: 5 archivos solo con tipos de Prisma son deuda de la Fase 6. Sí entra a `core-sin-consultas`.
- `registrarCambioAuditado` se importa desde 54 archivos de `src/` (no 35) y 10 tests lo mockean con `vi.mock` + `typeof import`.
- El «comentario falso» de `ALCANCE_CARTA_PUBLICA` ya lo corrigió el trabajo 1.13; hay que reescribirlo de nuevo cuando se mude.
- Las «3 mutaciones de seguridad» de la carta pública no estaban definidas; se definen en §5.2 (S1, S2, S3).
